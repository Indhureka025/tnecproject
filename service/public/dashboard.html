Why it stalled — in plain terms

The two date boxes on the real form ("EC Start Date" and "EC End Date") open a little pop-up calendar when you click them. Our robot was clicking into the box correctly, but wasn't finishing the job the same way a person clicking a day on that calendar does — so the website quietly saw both boxes as still empty. The website's own rule is: "don't search unless every required box is filled" — so it just stopped, silently, with no error message at all. That's exactly why this took hours to track down: nothing looked broken on screen, it just... did nothing.

Full technical trace (every request, response, and line of the website's own code we read to confirm this) is in poc/SELECTORS.md. The fix itself — clicking the actual calendar instead of typing into the box — is written and partly working; it now needs its last selector corrected, a small, well-understood task.

Should we take this project forward?

✅ Yes — continue, as planned

Nothing found tonight changes the recommendation from the original feasibility report. If anything, it sharpens it:

  • The free, no-login search path on the real government site is proven to work for every step except one, and that one step is a diagnosed, specific bug — not a dead end.
  • Everything else built around it — the queue, the audit trail, the human-in-the-loop console, the retry-on-rejected-CAPTCHA logic, the OCR for old certificates — is solid and has been tested repeatedly, including tonight.
  • Tonight is also a useful, honest data point: a government website can change its own form logic at any time without warning (this looks like a recent addition on their side), which is exactly why the original plan treats our own automation as a backup, not the main path. That recommendation still holds.

Recommended path, unchanged: a licensed data provider (Landeed / SurePass) as the main source for volume and reliability, with this automation kept as the fallback for cases the provider can't cover — and accepted as something that will occasionally need a small fix like tonight's, the same way any integration with a website you don't control does.

Idea — searching for many properties at once

The system was already built to handle more than one request at a time — this isn't a rebuild, it's turning on something the design already supports.

In plain terms: one person's time solving CAPTCHAs is the only fixed cost per property — everything else (opening the site, filling the form, reading the result) the robot does on its own, for as many properties as are queued up. The operator console already lists every open task, not just one, so this mostly means adding a way to submit a whole list at once, not building something new.

One real caution: sending a large batch of automated searches at the real government site in a short window risks the same kind of trouble we ran into tonight — a site that starts behaving oddly for automated traffic. Batch mode should pace itself deliberately, and — matching the same recommendation as above — is best used for the overflow a paid provider can't handle, not as the main way to process high volume.

Where things stand

We checked every official route. There is no government API for EC search — not from TNREGINET, not from API Setu. The workable path is a licensed data provider (Landeed / SurePass) as the main source, with our own supervised browser automation as a backup, both hidden behind one simple interface the ERP calls. Certified (court/bank-grade) ECs will always take 1–10 days because a government officer has to sign them.

The whole pipeline is built and tested — database, queue, the full 595-office list, the automation robot (proven against a stand-in portal), OCR for old scanned certificates, the certified-copy flow, and the ERP hand-off. It currently runs on sample data. Two things unlock real data: a sandbox key from a vendor, or running the robot from a server in India.

Frameworks & tools used

ToolCategoryWhat it's for, in plain terms
Node.js + TypeScriptLanguageThe programming language the whole service is written in — TypeScript catches mistakes before they reach real users.
FastifyWeb frameworkHandles the "front door" — receiving a request from the ERP and sending a reply.
PostgreSQLDatabaseStores every request, its status, and a full history — the record-keeper.
A job queueTask managementMakes sure lookups happen in order, retry automatically if something fails, and one slow request doesn't hold up the rest.
PlaywrightBrowser automationDrives a real web browser automatically — used only for the backup route, filling in the government site the way a person would.
Tesseract OCRText recognitionReads text out of old, scanned certificate images so they can be turned into structured data too.
Signed webhooksDeliveryThe mechanism that reliably sends the finished answer back to the ERP, and proves it really came from us.
Encrypted file storageDocumentsWhere the actual certificate files and summaries are kept, safely and privately.

None of this is exotic — every tool above is a mainstream, widely-used choice, picked because it's boring and reliable, not because it's novel. Full technical reasoning for each choice is in submission/TN-EC-Production-Architecture.pdf.
